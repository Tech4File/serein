# Serein — cross-platform account and device management

All three chat composers now offer a local emoji picker; Unicode emojis typed by system or external keyboards remain ordinary encrypted message text. GIFs and images pasted from a keyboard/pasteboard (and files selected or dropped where the platform allows) use the existing encrypted attachment transfer path. Android declares and accepts keyboard rich-content images/GIFs, web handles image clipboard/drop data, and iOS accepts GIF/image pasteboard items plus Files selection. This does not add a hosted GIF search/provider; keyboard GIFs that arrive only as a link remain text. The Serein speech-mark branding is shared across web favicon/PWA icons, Android adaptive launcher art, and the iOS app icon. These input and media paths are source-implemented and still require real-device/keyboard testing.


Serein has web, Android, and iOS account/contact/device clients. Source implements per-recipient-device messaging with two separately keyed client-side encryption layers and manual device-fingerprint verification; live messaging still uses static P-256 keys, not the experimental Rust/WASM ratchets. The web encrypted file-transfer path is source-implemented; native transfer and live cross-platform behavior still need verification. New backups in web and native source require DEFLATE before AES-GCM. The latest Android backup source received only a stubbed Java syntax check and the iOS backup source has not been built; neither is device-tested. Calls are not implemented and the apps do not request camera or microphone permissions. Background push delivery is not implemented. Email-provider delivery and live PostgreSQL/API flows remain unverified; `MAIL_DELIVERY=disabled` is the default and prevents registration.

Appearance settings offer System, Large, and Extra large text sizing. Web and Android use the shared generated scale tokens (1.15× and 1.3×; Android text has a 12sp minimum); iOS respects Dynamic Type and applies platform size-category floors. These are source-level behaviors and still need platform build/device verification.

The repository includes a first-party, dependency-free Rust media track/object routing core. It is an in-memory router only: there is no QUIC/WebTransport media service or calling feature. WebRTC has not been added. CI and gated release workflows are under `.github/workflows/`; hosted builds/signing have not been verified.

> **Security status:** `VERSION` is an unverified development snapshot, not a production security assurance. Live messages still use static P-256 ECDH → HKDF-SHA-256 → AES-256-GCM twice with two separately generated device key pairs; Layer 2 is independent of Layer 1 key material and encrypts the Layer 1 envelope for the target device. Users must compare and pin the combined device-key fingerprint through a separate trusted channel. A separate experimental Rust symmetric/X25519 Double Ratchet core now has a C ABI and browser/WASM bridge with bounded skipped keys and transactional AEAD tests, but it is not connected to app message flows, backend session establishment, or either mobile app. It has no authenticated prekey/session establishment, identity-signature layer, post-quantum layer, or independent cryptographic review. Therefore the deployed message protocol still has no forward-secret ratchet and does not protect a fully compromised endpoint or a break in the shared primitive family. Do not rely on it for high-risk communications.
>
> The intended protections are two application E2EE layers, with TLS in transit and app-private/OS-protected local key storage as separate protections. The second layer uses existing native crypto APIs and an independently generated device key pair; it is not a novel cipher or a claim of guaranteed stronger security. Manual fingerprint verification, static keys, key-change handling, and cross-platform interoperability still need review and testing.
>
> A server cannot reliably identify an “original” client from User-Agent, app version, Origin, CORS, or a hard-coded app secret; Postman can imitate these, and modified clients can extract embedded secrets. The server must treat every API as public and enforce authentication, authorization, validation, abuse limits, and audit controls. Origin checks/CSP added here are browser defense-in-depth, not a Postman block. Genuine mobile-app attestation requires platform verification (for example Play Integrity/App Attest), server-side nonce/signature validation, provider credentials, and testing on signed production builds. Web clients have no universal tamper-proof attestation. None of those attestation integrations is configured yet.
>
> Privacy controls added in source include account-scoped contact requests (generic response for matching/non-matching/ineligible verified accounts), a per-account discovery limit, request consent, opt-in email discoverability (off by default), presence visibility, and blocking. Latest Rust workspace tests passed (14 backend, 34 shared-core, 9 media-router); strict shared-core Clippy and the declared MSRV check also passed; these behaviors have not passed a live database/API smoke test. They are defense-in-depth only; the discovery limit is per account (not a trusted edge/IP limit), and timing/abuse testing remains necessary.

Media bytes are not packaged. New backup exports derive a stable per-account key locally from the authenticated account UUID, with no separate password prompt; legacy v1 backups still require the original password. The backend now checks the password and requires per-login email OTP before issuing a new verified-account session, so password-only sign-in does not return the account UUID. Latest Rust workspace tests passed (14 backend, 34 shared-core, 9 media-router); strict shared-core Clippy and the declared MSRV check also passed; provider delivery and the PostgreSQL/API smoke test remain unverified. Genuine-app attestation, media-byte packaging, cloud-provider selection, and mobile-assisted web history sync are not implemented. Android/iOS `.srbk` v2 export/import source now uses the stable account-ID key, retains v1 password restore, uses platform document pickers, and provides the one-time restore onboarding with duplicate-safe merge. Earlier Android debug/instrumentation APK compilation passed, but the latest backup codec source only passed a stubbed Java syntax compile; backup tests were not run on device, and iOS source remains unbuilt. Snapshots are limited to 64 MiB/100,000 messages and media references only.

## Run Serein web and API

Requirements: Rust stable, Docker (or PostgreSQL 14+), and a modern browser.

```sh
docker compose up -d postgres
cd backend
DATABASE_URL=postgres://serein:dev-only-change-me@localhost:5432/serein LISTEN_ADDR=0.0.0.0:8080 COOKIE_SECURE=false cargo run
```

Email verification is deliberately disabled by default. To enable registration, configure exactly one provider before starting the API:

- HTTPS mail API: `MAIL_DELIVERY=api`, `MAIL_API_URL=https://api.resend.com/emails` (or a compatible HTTPS endpoint), `MAIL_API_KEY=…`, and `MAIL_FROM='Serein <no-reply@your-domain.example>'`. The API key is sent only as a bearer header to that configured HTTPS origin; redirects, URL user-info/query strings, automatic proxy discovery, response-body logging, and provider error-body logging are disabled.
- SMTP: `MAIL_DELIVERY=smtp`, `SMTP_HOST=…`, `SMTP_TLS_MODE=starttls` with port 587 (default) or `implicit` with port 465, `MAIL_FROM=…`, and optionally both `SMTP_USERNAME` and `SMTP_PASSWORD`. Plaintext SMTP is rejected.

Configure verified sender/domain DNS and provider credentials outside source control. Use a provider key scoped to sending from this domain, place it in the server's secret manager/environment (never the browser/mobile config), and rotate it if it may have appeared in logs or shell history. The server sends it only to the configured provider; it remains in server process memory while running. Only then open `http://localhost:8080`, create an account, retrieve the six-digit code from email, and verify it before sign-in. Codes are hashed, expire after ten minutes, allow five guesses, and have a 60-second resend delay with a per-account daily send cap. These controls are not a substitute for edge/IP rate limiting. The provider setup and email receipt have not been verified here. Registration passwords require at least eight Unicode code points, one ASCII uppercase letter, one ASCII lowercase letter, one digit, and no more than 1024 UTF-8 bytes; sign-in does not reapply signup composition rules. `/status` shows sanitized API, database, web-interface, and email-provider configuration states; `/healthz` is the machine-readable readiness check. Email status indicates configuration only, so test by registering with an inbox you control and verifying the six-digit code. Test web chat with two verified disposable accounts on separate browser profiles/devices: enroll both device keys, accept the contact request, compare the complete fingerprints out-of-band, explicitly trust every active recipient-device fingerprint on each sender browser, then send text. Messages can queue for offline devices and are decrypted only on the client. The web attachment path is source-implemented but unverified; test only with disposable accounts and non-sensitive files. Calls are not implemented; the app does not request microphone or camera permissions.

For a static frontend hosted separately from the API, set `frontend/web/config.js`'s `apiBase` to the API base URL, configure `ALLOWED_WEB_ORIGINS` on the API to the exact origin(s) of the browser page (scheme, host, and non-default port—not just the API host), use HTTPS/WSS, and keep the frontend/API on the same site (for example, sibling subdomains) so the secure Lax session cookie is sent. The API now rejects disallowed `Origin` headers and emits a CSP plus common security headers on API responses and when it serves the bundled web UI. If the web UI is hosted separately, configure equivalent document security headers there too. This is browser defense-in-depth, not client attestation. Cross-site cookie behavior still needs deployment testing. The web UI uses the Rust/WASM core for username and registration-password rules when `frontend/web/serein_core.wasm` is built and present; otherwise local JavaScript fallbacks support static previews. CI builds and includes the WASM file in its web artifact.

## Encrypted file transfer (web client source implemented; unverified)

The web composer can upload a selected file after every recipient-device fingerprint has been explicitly verified. The browser generates a per-transfer AES-256-GCM key, encrypts fixed-size chunks with unique per-chunk nonces and transfer/index-bound AAD, wraps file metadata/key separately for the sending device and each active recipient device, then sends an encrypted chat notice containing only the transfer ID and display metadata. The server stores opaque encrypted chunks; it never receives filenames or plaintext. On download the browser checks each server SHA-256 transport digest, authenticates/decrypts each chunk, checks total size against the encrypted manifest and chat notice, then offers a save link and uses native browser image/audio/video playback only for supported MIME types/codecs. Unsupported preview types fall back to saving the decrypted file.

`POST /api/v1/transfers` requires exactly the sending session plus every active recipient device in the encrypted manifest set. Upload each chunk with `PUT /api/v1/transfers/{id}/chunks/{index}`, `Content-Type: application/octet-stream`, and `X-Chunk-SHA256: <hex SHA-256>`. `GET /api/v1/transfers` lists visible transfers; chunk downloads are authenticated; `POST /api/v1/transfers/{id}/ack` acknowledges a transfer; the originating device may `DELETE /api/v1/transfers/{id}` to abort.

Limits are 256 KiB ciphertext per chunk, 512 chunks / 64 MiB ciphertext per transfer, 32 active participant devices per transfer, 100 live transfers and 256 MiB of active transfer data per participant, and a seven-day expiry. Byte-identical chunk retries are idempotent, but the current web upload is sequential and does not yet persist resumable progress across reloads or provide pause/cancel controls. The SHA-256 value is a transport checksum only; confidentiality and tamper detection come from the browser's AEAD key/tags and per-device envelopes. This implementation is not independently reviewed, has not been exercised against a live backend/two-account session, and is web-only.

## Repository

- `frontend/web/` — static HTML/CSS/JavaScript; no npm runtime packages. Includes first-party `serein-avatar` and `serein-button` Web Components.
- `crates/serein-core/` — first-party Rust domain validators plus an experimental symmetric/X25519 Double Ratchet core and C/WASM ABI. The crypto primitives are backed by the listed Cargo dependencies; the ratchets are not connected to live app messaging or authenticated session setup. Includes packet framing, which is not a secure transport.
- `crates/serein-moq-engine/` — first-party media-track/object router with per-subscriber and aggregate queue bounds; transport-agnostic, not interoperable MOQT on the wire.
- `design/tokens.json` + `scripts/generate-design-tokens.py` — single source for web CSS, Android Java, and iOS Swift design tokens; generated outputs are checked in. The Python scripts under `scripts/` are developer/CI utilities only (version consistency, design-token generation, and source ZIP creation); **Python is not an application runtime dependency**.
- `backend/` — Rust account/session/contact/device APIs and OTP email delivery. Authenticated message submit/history/ACK/WebSocket routes relay opaque ciphertext for the web client; the server does not decrypt message bodies. Encrypted attachment-chunk APIs have a web client path in source, but live delivery is unverified; native transfer remains unwired. `/api/v1/security/capabilities` reports current implementation status. Startup creates/updates schema directly; SQL migrations are not automatically applied.
- `apps/android/` — native Java client with HTTPS auth, contacts, shared text-scale tokens, and device-session API wiring; calling is not implemented.
- `apps/ios/` — native SwiftUI client with URLSession auth, contacts, Dynamic Type sizing, preferences, and device-session API wiring; calling is not implemented.
- `.github/workflows/` — CI and release-artifact workflows; hosted builds/signing have not been verified.

## Common application logic — staged migration, not yet complete

Use the existing Rust `serein-core` as the shared **domain/protocol core**, not a new UI framework. It now includes crypto dependencies for experimental ratchet primitives and C/WASM APIs; the backend links it as Rust, and the browser bridge exposes its ratchet API. New Android CMake/JNI and iOS XCFramework/Swift wiring links the core and exposes a version smoke check; native message/transfer flows still do not call the ratchet APIs. This is the first native-linking milestone, not completed E2EE integration.

Move platform-independent rules into `serein-core`: input and registration policy, normalized domain models, endpoint/request semantics, connection-health classification, OTP/resend state, contact/privacy/device transitions, and stable error/result codes. Keep only rendering, Fetch/URLSession/Android networking, OS-backed storage, permissions, accessibility, and lifecycle handling in each shell. The user has specified two application E2EE layers in addition to TLS and protected local storage. Web, Android, and iOS source now implement the same documented dual-device-key message format with platform-native crypto/storage APIs. This is not independently reviewed; shared conformance vectors and verified cross-platform runtime tests remain required.

The shared-core integration path is WebAssembly for web, a Rust static library plus Android CMake/JNI for Android, and a generated XCFramework plus C/Swift bridge for iOS. `scripts/build_native_core.sh android|ios` builds the target artifacts under ignored `target/native-core/`; generated binaries are never committed. Android/iOS currently call only the core version smoke API, not ratchet/message APIs. CI now configures native linkage plus Android API 26/35 instrumentation and an iOS simulator launch smoke test; these newly changed builds have not yet run. The crypto engine is not “shared for messaging” until live message/file paths invoke the same ratchet behavior and cross-platform vectors pass on all supported platforms.

**Shared message-input limit:** `serein-core` defines a 4,000 Unicode-scalar limit and 3,600-character warning threshold; the C/WASM ABI exposes both to the web client. The web composer truncates over-limit paste/input without splitting surrogate pairs and shows the remaining count from 90%. Unsent drafts are kept in memory per contact for the current tab. Browser and Rust-core tests cover Unicode counting and threshold behavior; native composer wiring is not present.

**First vertical slice underway:** registration-password rules are now defined/tested in `serein-core`, consumed by the backend, exposed through its C/WASM ABI, and used by the web UI when the WASM core is present (with the existing local-preview fallback). Android and iOS still duplicate the UI-only password checklist; their JNI/Swift imports and conformance runs are the next migration gate and have not been implemented or built. Continue feature-by-feature only after the native build pipeline can verify both bridges.

Each client generates separate Layer 1 and Layer 2 P-256 ECDH key pairs, publishes only their public JWKs, and derives device-pair-specific secrets independently. The combined key-bundle fingerprint is compared and pinned locally; a change is not automatically trusted. New messages encrypt the Layer 1 envelope with Layer 2 using routing metadata as AAD; the backend stores the versioned opaque envelope. The static ECDH design has no forward-secret ratchet or automated recovery/rotation and has not had independent review. Browser non-extractable keys are not guaranteed hardware-backed; native and cross-platform runtime behavior remain unverified.

`/security.html` polls the selected server's sanitized `/api/v1/security/capabilities` every 30 seconds, reporting web messaging active alongside native, forward-secrecy, and independent-review gaps. It is an implementation-status report, not an audit.

## Development and versioning

`VERSION` is the **single editable application-version source** and contains the current internal development snapshot—not an Alpha/Beta or release claim. On each code-change task, increment only this file. `python3 scripts/sync_versions.py` regenerates Cargo workspace/package-lock, web, and iOS build metadata; `python3 scripts/check_versions.py` also performs that sync before validating mirrors and platform floors. CI invokes the sync before every isolated build job, so a stale generated mirror cannot block a push or ship an old iOS What's New value. After code changes, refresh and audit the one root `serein-source.zip`. A tag does not auto-publish a GitHub Release. A new `version-consistency` CI job runs on every branch/tag push, PR, and manual run; it checks SemVer, all product Cargo package versions, the web version, Android’s `versionName` source, iOS `MARKETING_VERSION` and the What's New version, and platform floors plus exact stable tag matches. On stable version tags it also rejects a version that is not greater than existing stable tags. Signed release jobs require a matching stable `vX.Y.Z` tag and the repository variable `SEREIN_RELEASE_APPROVED=true`; leave it unset until the implementation and release gates are reviewed. Release builds are uploaded as workflow artifacts, not automatically published as a GitHub Release. Dependabot version-update schedules have been removed; dependency bumps are maintainer-driven, while CI resolves/builds dependencies on every push and pull request. GitHub's repository-level security alerts are separate. Markdown notes other than this root README are ignored by Git but remain in the complete source archive.

## Next implementation phases

1. **Opaque transfer transport (implemented and compiled from backend source; live service integration unverified):** upload/download encrypted chunks, per-chunk SHA-256 integrity, resumable idempotent writes, participant/device authorization, quota limits, expiry, and device-specific encrypted manifests. The service sees routing and size/timing metadata but never receives filenames or plaintext. At transfer creation, manifests cover the current sending session plus every currently active recipient device; other sender devices do not inherit an in-progress transfer, and devices enrolled later cannot decrypt old transfers.
2. **Harden dual-layer E2EE:** finish shared conformance vectors and cross-platform live tests; design authenticated key epochs, forward-secret ratcheting, recovery/history transfer, and robust device/key-change handling; then obtain independent cryptographic review. Current device-pair keys are static and require manual out-of-band fingerprint verification.
3. **Cross-platform file-transfer completion (partial):** a web-only encrypted upload/download/preview path is now present in source, with authenticated per-device manifests and chunk AEAD. Add native Android/iOS adapters, durable resumable progress, pause/retry controls, supported-codec/device tests, and live two-account/API coverage before treating transfers as reliable.
4. **Calls (not implemented):** establish reviewed call signaling and identity-bound session keys, then implement encrypted audio/video over an interoperable QUIC/MoQ stack with congestion control, loss/recovery, device switching, and group limits. The old QUIC echo demo has been removed, and the in-memory object router is not a call transport. The current no-new-dependencies-outside-email rule blocks adopting a maintained QUIC/MoQ implementation; do not replace it with custom TLS/QUIC or claim calling is available.

## Current limits

- Registration email verification and per-login email OTP are implemented in source. Latest Rust workspace tests passed (14 backend, 34 shared-core, 9 media-router); strict shared-core Clippy and the declared MSRV check also passed; provider credentials, DNS, mail receipt, and end-to-end database/API verification remain unverified. There is no password reset, account recovery, or IP/edge rate limiting; independent security review is still required.
- The new transfer API is opaque ciphertext storage/routing. Web and native sender/receiver paths are present in source, but live transfers and mobile-device behavior have not been verified; native parity remains incomplete. It is not a production encrypted-file feature until the key lifecycle and client work above are tested and reviewed. Server metadata (participants, device IDs, byte counts, and timing) is visible.
- Contact discovery by username or verified email now creates a pending request; the recipient must accept. Unknown/ineligible targets get the same response body as eligible targets, and submitters cannot inspect request status before acceptance (to reduce enumeration); requests expire after 30 days and cap at 50 outgoing/100 incoming pending requests; per-account discovery is limited to 10 attempts/hour. Privacy settings control email discovery, request acceptance, and presence; blocks remove the relationship and deny new message/transfer authorization. Timing and distributed abuse resistance are not verified, and there is no trusted edge/IP rate limiter. Mobile-number discovery is not implemented.
- The user-defined two-application-layer message design is now wired in source for web, Android, and iOS. The server stores two public P-256 keys per device and opaque versioned ciphertext; clients derive separate device-pair secrets and require a user-verified combined fingerprint. It remains static ECDH without forward secrecy, lacks automated key rotation/recovery, and has not had independent review or cross-platform runtime verification. No audited or production security claim is made.
- Calls and media are not implemented. The old QUIC echo demo was removed; the in-memory router is not a call stack. WebRTC is intentionally excluded.
- Native apps include account-management and chat API flows, native device-key protection, dual-layer message encryption, and encrypted local history in source. Android compilation/runtime and iOS build/runtime must be rechecked for this dual-layer update; cross-platform crypto interoperability is unverified.
- Dependency updates are maintainer-driven and must be reviewed; no Dependabot version-update schedule is configured. The experimental shared Rust crypto core currently uses `aes-gcm`, `hkdf`, `hmac`, `sha2`, `x25519-dalek`, and `zeroize`; these are primitive libraries, not an approved complete E2EE protocol implementation. Do not add further cryptographic dependencies without approval. No interoperable QUIC/MOQT transport is implemented.
