# Serein — cross-platform account and device management

Serein has web and native account/contact/device clients. Web text chat encrypts messages to recipient-device keys and uses the authenticated opaque-ciphertext queue; every recipient-device fingerprint must be compared out-of-band and confirmed in the browser first. A web file-transfer path now encrypts chunk data and per-device manifests in the browser, uploads opaque chunks, and supports authenticated download/decryption with browser-native image/audio/video preview where supported. These new attachment changes have not been live-tested or audited. Native Android/iOS chat and file transfer are not wired yet. Audio/video calls remain permission preflight only; QUIC media transport is not implemented. Email provider delivery, Rust/native builds, and live API integration are not verified here. `MAIL_DELIVERY=disabled` is the default and prevents registration.

Text sizing now follows the browser/OS default unless a user chooses Large or Extra large in Appearance/Settings; app-adjusted text has a 10-point minimum in the native/web UI helpers. The web and native Calls screens now provide microphone/camera permission preflight and retry guidance, but permission is not media transport: no call is placed, QUIC signaling/media is still absent, and the mute/video/speaker controls remain unavailable. Device-local pending setup is not a shared active call session.

The repository also contains a first-party, dependency-free Rust media track/object routing core and a separate WebTransport/QUIC echo spike. The routing core is not an MOQT wire implementation and the echo server is not a call service. WebRTC has not been added. CI and gated release workflows are under `.github/workflows/`; no release artifacts have been verified.

> **Security status:** `VERSION` is an unverified development snapshot, not a production security assurance. Web text messages now use static P-256 ECDH → HKDF-SHA-256 → AES-256-GCM and require users to compare and pin each recipient-device fingerprint through a separate trusted channel. This web implementation has not had independent review, has no forward secrecy or automated key recovery/rotation, and native messaging is absent. Do not rely on it for high-risk communications.
>
> “Three layers” means independent protections—not custom ciphers stacked on one payload: (1) authenticated TLS in transit, (2) client-side E2EE with authenticated/verified device identities, and (3) OS-backed, device-local key/storage protection. The web text path is implemented with manual fingerprint verification, but its cryptographic lifecycle has not been reviewed; native OS-backed messaging storage is still missing. Extra nested encryption does not substitute for authenticated key agreement or forward secrecy.
>
> A server cannot reliably identify an “original” client from User-Agent, app version, Origin, CORS, or a hard-coded app secret; Postman can imitate these, and modified clients can extract embedded secrets. The server must treat every API as public and enforce authentication, authorization, validation, abuse limits, and audit controls. Origin checks/CSP added here are browser defense-in-depth, not a Postman block. Genuine mobile-app attestation requires platform verification (for example Play Integrity/App Attest), server-side nonce/signature validation, provider credentials, and testing on signed production builds. Web clients have no universal tamper-proof attestation. None of those attestation integrations is configured yet.
>
> Privacy controls added in source include account-scoped contact requests (generic response for matching/non-matching/ineligible verified accounts), a per-account discovery limit, request consent, opt-in email discoverability (off by default), presence visibility, and blocking. They are defense-in-depth only; the discovery limit is per account (not a trusted edge/IP limit), timing/abuse testing remains necessary, and none of these changes has passed a database/API build test.

## Run Serein web and API

Requirements: Rust stable, Docker (or PostgreSQL 14+), and a modern browser.

```sh
docker compose up -d postgres
cd backend
DATABASE_URL=postgres://serein:dev-only-change-me@localhost:5432/serein LISTEN_ADDR=0.0.0.0:8080 COOKIE_SECURE=false cargo run
```

Email verification is deliberately disabled by default. To enable registration, configure exactly one provider before starting the API:

- HTTPS mail API: `MAIL_DELIVERY=api`, `MAIL_API_URL=https://api.resend.com/emails` (or a compatible HTTPS endpoint), `MAIL_API_KEY=…`, and `MAIL_FROM='Serein <no-reply@your-domain.example>'`. The API key is sent only as a bearer header to that configured HTTPS origin; redirects, URL user-info/query strings, automatic proxy discovery, response-body logging, and provider error-body logging are disabled.
- SMTP: `MAIL_DELIVERY=smtp`, `SMTP_HOST=…`, `SMTP_TLS_MODE=starttls` with port 587 (default) or `implicit` with port 465, `MAIL_FROM=…`, and optionally both `SMTP_USERNAME` and `SMTP_PASSWORD`. Plaintext SMTP is rejected.

Configure verified sender/domain DNS and provider credentials outside source control. Use a provider key scoped to sending from this domain, place it in the server's secret manager/environment (never the browser/mobile config), and rotate it if it may have appeared in logs or shell history. The server sends it only to the configured provider; it remains in server process memory while running. Only then open `http://localhost:8080`, create an account, retrieve the six-digit code from email, and verify it before sign-in. Codes are hashed, expire after ten minutes, allow five guesses, and have a 60-second resend delay with a per-account daily send cap. These controls are not a substitute for edge/IP rate limiting. The provider setup and email receipt have not been verified here. Registration passwords require at least eight Unicode code points, one ASCII uppercase letter, one ASCII lowercase letter, one digit, and no more than 1024 UTF-8 bytes; sign-in does not reapply signup composition rules. `/status` shows sanitized API, database, web-interface, and email-provider configuration states; `/healthz` is the machine-readable readiness check. Email status indicates configuration only, so test by registering with an inbox you control and verifying the six-digit code. Test web chat with two verified disposable accounts on separate browser profiles/devices: enroll both device keys, accept the contact request, compare the complete fingerprints out-of-band, explicitly trust every active recipient-device fingerprint on each sender browser, then send text. Messages can queue for offline devices and are decrypted only on the client. The web attachment path is source-implemented but unverified; test only with disposable accounts and non-sensitive files. Calls remain unavailable beyond permission preflight.

For a static frontend hosted separately from the API, set `frontend/web/config.js`'s `apiBase` to the API base URL, configure `ALLOWED_WEB_ORIGINS` on the API to the exact origin(s) of the browser page (scheme, host, and non-default port—not just the API host), use HTTPS/WSS, and keep the frontend/API on the same site (for example, sibling subdomains) so the secure Lax session cookie is sent. The API now rejects disallowed `Origin` headers and emits a CSP plus common security headers on API responses and when it serves the bundled web UI. If the web UI is hosted separately, configure equivalent document security headers there too. This is browser defense-in-depth, not client attestation. Cross-site cookie behavior still needs deployment testing. The web UI uses the Rust/WASM core for username and registration-password rules when `frontend/web/serein_core.wasm` is built and present; otherwise local JavaScript fallbacks support static previews. CI builds and includes the WASM file in its web artifact.

## First testing phase: local web/API, then mobile

1. Before pushing, keep `.env`, provider credentials, Android keystores, Apple certificates/profiles, and all user data out of Git. Only root `README.md` is tracked Markdown; create the complete source ZIP (including ignored documentation) with `python3 scripts/create_source_archive.py`. The generated archive is saved as the ignored root-level `serein-source.zip`. This checkout has no `Cargo.lock`; after installing Rust 1.85+, generate/review one with `cargo generate-lockfile`, then run `cargo check --workspace` and `cargo test --workspace` before committing it.
2. Push `main` to your GitHub repository and wait for **Actions → Checks and mobile builds** to pass. CI uploads the static web app, an Android debug APK plus an unsigned release APK, and an iOS Simulator app zip. Use only `app-debug.apk` for sideload testing. The simulator `.app` zip is not an iPhone IPA.
3. For local web/API testing, use Docker Compose PostgreSQL and the local-only settings in `.env.example`. Copy it to ignored `.env`, then configure a real test-mail provider: `MAIL_DELIVERY=disabled` deliberately prevents registration. From the repo root run `docker compose up -d postgres`; in a second terminal run `cd backend`, `set -a; source ../.env; set +a`, then `cargo run`. Open `http://localhost:8080` and test registration, OTP verification, sign-in, contacts, settings, device management, and web text messaging with disposable accounts. For chat, verify the full fingerprints through another trusted channel before pressing Send. Use Connection settings to select and check a self-hosted API origin; the web server must allow the exact browser origin. Detailed checks and the manual smoke-test command are in the ignored `docs/TESTING_GUIDE.md` and in the complete source ZIP.
4. After web/API tests, Android debug installs on API 26+; the CI debug APK is signed with a temporary debug key, not a Play signing key. Android/iOS native messaging is not connected yet. Native apps require a reachable HTTPS API; local `localhost` on a phone refers to the phone itself.
5. For physical iOS device testing, the new manual **iOS Ad Hoc test IPA** workflow requires Apple signing secrets and an unexpired Ad Hoc profile containing the test devices' UDIDs. It creates a test IPA without the stable-release approval gate. The existing `release.yml` remains separately gated and only accepts a stable `X.Y.Z` version/tag; it creates signed Android release outputs and App Store Connect/Ad Hoc iOS IPAs but does not upload to stores.

A green CI run is not a product/security sign-off: the PostgreSQL/mail smoke test is manual, Rust/mobile builds have not been run in this environment, browser messaging and the new web attachment path have not been audited, and native chat/file transfer and live calls remain incomplete. See `BUILDING.md` (in the complete archive) for artifact and signing details.

## Encrypted file transfer (web client source implemented; unverified)

The web composer can upload a selected file after every recipient-device fingerprint has been explicitly verified. The browser generates a per-transfer AES-256-GCM key, encrypts fixed-size chunks with unique per-chunk nonces and transfer/index-bound AAD, wraps file metadata/key separately for the sending device and each active recipient device, then sends an encrypted chat notice containing only the transfer ID and display metadata. The server stores opaque encrypted chunks; it never receives filenames or plaintext. On download the browser checks each server SHA-256 transport digest, authenticates/decrypts each chunk, checks total size against the encrypted manifest and chat notice, then offers a save link and uses native browser image/audio/video playback only for supported MIME types/codecs. Unsupported preview types fall back to saving the decrypted file.

`POST /api/v1/transfers` requires exactly the sending session plus every active recipient device in the encrypted manifest set. Upload each chunk with `PUT /api/v1/transfers/{id}/chunks/{index}`, `Content-Type: application/octet-stream`, and `X-Chunk-SHA256: <hex SHA-256>`. `GET /api/v1/transfers` lists visible transfers; chunk downloads are authenticated; `POST /api/v1/transfers/{id}/ack` acknowledges a transfer; the originating device may `DELETE /api/v1/transfers/{id}` to abort.

Limits are 256 KiB ciphertext per chunk, 512 chunks / 64 MiB ciphertext per transfer, 32 active participant devices per transfer, 100 live transfers and 256 MiB of active transfer data per participant, and a seven-day expiry. Byte-identical chunk retries are idempotent, but the current web upload is sequential and does not yet persist resumable progress across reloads or provide pause/cancel controls. The SHA-256 value is a transport checksum only; confidentiality and tamper detection come from the browser's AEAD key/tags and per-device envelopes. This implementation is not independently reviewed, has not been exercised against a live backend/two-account session, and is web-only.

## Repository

- `frontend/web/` — static HTML/CSS/JavaScript; no npm runtime packages. Includes first-party `serein-avatar` and `serein-button` Web Components.
- `crates/serein-core/` — first-party zero-dependency Rust domain validators and C/WASM ABI; used by the API and the browser's optional WASM validator. Includes an allocation-free packet framing helper, not a secure transport or integrated network protocol.
- `crates/serein-moq-engine/` — first-party media-track/object router with per-subscriber and aggregate queue bounds; transport-agnostic, not interoperable MOQT on the wire.
- `design/tokens.json` + `scripts/generate-design-tokens.py` — single source for web CSS, Android Java, and iOS Swift design tokens; generated outputs are checked in. The Python scripts under `scripts/` are developer/CI utilities only (version consistency, design-token generation, and source ZIP creation); **Python is not an application runtime dependency**.
- `backend/` — Rust account/session/contact/device APIs and OTP email delivery. Authenticated message submit/history/ACK/WebSocket routes relay opaque ciphertext for the web client; the server does not decrypt message bodies. Encrypted attachment-chunk APIs have a web client path in source, but live delivery is unverified; native transfer remains unwired. `/api/v1/security/capabilities` reports current implementation status. Startup creates/updates schema directly; SQL migrations are not automatically applied.
- `media-transport-spike/` — older isolated WebTransport/QUIC datagram echo experiment; not MoQ and not a calling service.
- `apps/android/` — native Java client with HTTPS auth, contacts, app-wide text scaling, and device-session API wiring; Calls checks runtime microphone/camera permissions but does not connect a call.
- `apps/ios/` — native SwiftUI client with URLSession auth, contacts, Dynamic Type-aware app text sizing, preferences, and device-session API wiring; Calls checks microphone/camera permissions but does not connect a call.
- `.github/workflows/` — CI and release-artifact workflows; hosted builds/signing have not been verified.

## Common application logic — staged migration, not yet complete

Use the existing dependency-free Rust `serein-core` as the shared **domain/protocol core**, not a new UI framework. The backend links it as Rust; the browser can call its WASM build. Android and iOS are still separate native API/UI clients and **do not yet import the Rust core**. This is an acknowledged parity gap, not a completed cross-platform architecture.

Move platform-independent rules into `serein-core`: input and registration policy, normalized domain models, endpoint/request semantics, connection-health classification, OTP/resend state, contact/privacy/device transitions, and stable error/result codes. Keep only rendering, Fetch/URLSession/Android networking, OS-backed storage, permissions, accessibility, and lifecycle handling in each shell. The user has specified the three-layer E2EE design. The web message path uses platform WebCrypto only and is not independently reviewed. Native clients must implement the same documented key/context format with OS crypto/key-storage APIs before native messaging can be enabled.

The incremental integration path is the existing C ABI: WebAssembly for web, JNI/NDK for Android, and a C/Swift bridge plus a Rust static library for iOS. All three clients should call the same Rust functions and run the same checked-in conformance vectors. CI should build the core for each target and then build each app; a feature is not “shared” until the vectors pass on all supported platforms. This adds no application framework or non-mail third-party dependency. Do not copy generated binaries into source control.

**Shared message-input limit:** `serein-core` defines a 4,000 Unicode-scalar limit and 3,600-character warning threshold; the C/WASM ABI exposes both to the web client. The web composer truncates over-limit paste/input without splitting surrogate pairs and shows the remaining count from 90%. Unsent drafts are kept in memory per contact for the current tab. Browser and Rust-core tests cover Unicode counting and threshold behavior; native composer wiring is not present.

**First vertical slice underway:** registration-password rules are now defined/tested in `serein-core`, consumed by the backend, exposed through its C/WASM ABI, and used by the web UI when the WASM core is present (with the existing local-preview fallback). Android and iOS still duplicate the UI-only password checklist; their JNI/Swift imports and conformance runs are the next migration gate and have not been implemented or built. Continue feature-by-feature only after the native build pipeline can verify both bridges.

The web client generates a non-extractable P-256 ECDH device private key with WebCrypto, persists it in IndexedDB, registers only its public JWK to the authenticated account/device, and fetches keys for accepted contacts. It derives per-device keys with ECDH/HKDF, displays full fingerprints, and requires users to compare and pin them locally. A changed fingerprint is not automatically trusted. The message send/receive path uses AES-GCM envelopes with routing metadata bound as AAD; the backend stores opaque envelopes. This design is static ECDH without forward secrecy, has no automated key recovery/rotation, has not had independent review, and is web-only. Browser non-extractable storage is not guaranteed hardware-backed.

`/security.html` polls the selected server's sanitized `/api/v1/security/capabilities` every 30 seconds, reporting web messaging active alongside native, forward-secrecy, and independent-review gaps. It is an implementation-status report, not an audit.

## Development and versioning

`VERSION` is manually maintained and currently `0.4.0-dev.7`, an internal development snapshot—not an Alpha/Beta or release claim. For each requested code-change task, manually increment the development prerelease counter, synchronize all version sources, run the version checker, then refresh and audit the single root `serein-source.zip`. Version bumps are not automatic and a tag does not auto-publish a GitHub Release. A new `version-consistency` CI job runs on every branch/tag push, PR, and manual run; it checks SemVer, all product Cargo package versions, the web version, Android’s `versionName` source, iOS `MARKETING_VERSION` and the What's New version, and platform floors plus exact stable tag matches. On stable version tags it also rejects a version that is not greater than existing stable tags. Signed release jobs require a matching stable `vX.Y.Z` tag and the repository variable `SEREIN_RELEASE_APPROVED=true`; leave it unset until the implementation and release gates are reviewed. Release builds are uploaded as workflow artifacts, not automatically published as a GitHub Release. Dependabot version-update schedules have been removed; dependency bumps are maintainer-driven, while CI resolves/builds dependencies on every push and pull request. GitHub's repository-level security alerts are separate. Markdown notes other than this root README are ignored by Git but remain in the complete source archive.

## Next implementation phases

1. **Opaque transfer transport (implemented in backend source; unbuilt):** upload/download encrypted chunks, per-chunk SHA-256 integrity, resumable idempotent writes, participant/device authorization, quota limits, expiry, and device-specific encrypted manifests. The service sees routing and size/timing metadata but never receives filenames or plaintext. At transfer creation, manifests cover the current sending session plus every currently active recipient device; other sender devices do not inherit an in-progress transfer, and devices enrolled later cannot decrypt old transfers.
2. **Extend web E2EE across clients:** implement the same message format and authenticated device-key lifecycle in Android and iOS using native crypto/storage; design forward secrecy, rotation, recovery, and robust key-change handling; run shared conformance tests and independent review. The current web path requires manual out-of-band fingerprint verification and is static ECDH without forward secrecy.
3. **Cross-platform file-transfer completion (partial):** a web-only encrypted upload/download/preview path is now present in source, with authenticated per-device manifests and chunk AEAD. Add native Android/iOS adapters, durable resumable progress, pause/retry controls, supported-codec/device tests, and live two-account/API coverage before treating transfers as reliable.
4. **Calls (not implemented):** establish reviewed call signaling and identity-bound session keys, then implement encrypted audio/video over an interoperable QUIC/MoQ stack with congestion control, loss/recovery, device switching, and group limits. The current QUIC echo and object router are not call transports. The current no-new-dependencies-outside-email rule blocks adopting a maintained QUIC/MoQ implementation; do not replace it with custom TLS/QUIC or claim a call works.

## Current limits

- OTP email code paths are implemented but provider credentials, DNS, mail receipt, build, and end-to-end verification are not verified. There is no password reset, account recovery, or IP/edge rate limiting; independent security review is still required.
- The new transfer API is opaque ciphertext storage/routing. A web sender/receiver path is present in source but has not been built or live-tested; Android/iOS clients are not integrated. It is not a production encrypted-file feature until the key lifecycle and client work above are tested and reviewed. Server metadata (participants, device IDs, byte counts, and timing) is visible.
- Contact discovery by username or verified email now creates a pending request; the recipient must accept. Unknown/ineligible targets get the same response body as eligible targets, and submitters cannot inspect request status before acceptance (to reduce enumeration); requests expire after 30 days and cap at 50 outgoing/100 incoming pending requests; per-account discovery is limited to 10 attempts/hour. Privacy settings control email discovery, request acceptance, and presence; blocks remove the relationship and deny new message/transfer authorization. Timing and distributed abuse resistance are not verified, and there is no trusted edge/IP rate limiter. Mobile-number discovery is not implemented.
- The user-defined three-layer design now has a working web text-message path. The server stores public P-256 keys bound to authenticated account/device sessions; browser private keys are non-extractable WebCrypto keys in IndexedDB; users locally pin exact, separately compared peer fingerprints; messages are encrypted per recipient device and delivered as opaque AES-GCM envelopes. This is not independently reviewed, lacks forward secrecy and automated key rotation/recovery, and is not implemented in Android/iOS. No audited or production security claim is made.
- Calls and media are not implemented. The QUIC spike is not a call stack; WebRTC is intentionally excluded.
- Native apps now include account-management API wiring and OTP entry/resend flows, but have no native message encryption/transport or encrypted history store. Android/iOS build outputs and compatibility have not been verified here.
- Existing third-party dependencies remain. Two new crates are permitted only for OTP mail delivery (`lettre` SMTP and `reqwest` HTTPS API); both are exact-pinned. Dependency updates are maintainer-driven and must be reviewed; no Dependabot version-update schedule is configured. No new crypto, media, QUIC, or MoQ dependencies were added; real interoperable QUIC/MOQT is therefore not implemented.
