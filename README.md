# Serein — cross-platform account and device management

Serein is a cross-platform account, contact, and device-management application with web and native clients. User-facing messaging is not available yet. The backend has an authenticated, quota-bounded opaque-ciphertext chunk-transfer API: resumable/idempotent uploads, per-chunk SHA-256 integrity checks, seven-day expiry, and per-device encrypted manifest envelopes for the sender's and recipient's currently active devices. It stores no filenames or plaintext manifest. This is transport plumbing only: no client currently creates/decrypts those envelopes. A legacy browser shared-passphrase messaging prototype remains in source but is no longer enabled through the account flow; current web/native clients expose account/contact/device features, not secure messaging. No client currently implements reviewed device-key exchange or audited end-to-end encryption. Email provider delivery, compilation, and end-to-end verification remain unverified. `MAIL_DELIVERY=disabled` is the default and prevents registration.

The repository also contains a first-party, dependency-free Rust media track/object routing core and a separate WebTransport/QUIC echo spike. The routing core is not an MOQT wire implementation and the echo server is not a call service. WebRTC has not been added. CI and gated release workflows are under `.github/workflows/`; no release artifacts have been verified.

> **Security status:** `VERSION` is an unverified development snapshot, not a production secure messenger. Passwords are hashed with Argon2id and session tokens are opaque, random, and stored hashed server-side. These measures do not make the service production-ready. Secure messaging is disabled; a legacy shared-passphrase prototype remains in source but is not available through the current account flow. No reviewed device-key protocol or forward secrecy is implemented. Do not use the service for sensitive communications.
>
> “Three layers” should mean independent protections—not three custom ciphers stacked on one payload: (1) authenticated TLS in transit, (2) a reviewed client-side E2EE protocol with authenticated device keys, and (3) OS-backed, device-local key/storage protection. Only TLS/session handling is established; the client E2EE/key lifecycle and native storage protections still need implementation and review. Extra nested encryption does not substitute for authenticated key agreement or forward secrecy.
>
> A server cannot reliably identify an “original” client from User-Agent, app version, Origin, CORS, or a hard-coded app secret; Postman can imitate these, and modified clients can extract embedded secrets. The server must treat every API as public and enforce authentication, authorization, validation, abuse limits, and audit controls. Origin checks/CSP added here are browser defense-in-depth, not a Postman block. Genuine mobile-app attestation requires platform verification (for example Play Integrity/App Attest), server-side nonce/signature validation, provider credentials, and testing on signed production builds. Web clients have no universal tamper-proof attestation. None of those attestation integrations is configured yet.
>
> Privacy controls added in source include account-scoped contact requests (generic response for matching/non-matching/ineligible verified accounts), a per-account discovery limit, request consent, opt-in email discoverability (off by default), presence visibility, and blocking. They are defense-in-depth only; the discovery limit is per account (not a trusted edge/IP limit), timing/abuse testing remains necessary, and none of these changes has passed a database/API build test.

## Run Serein web and API

Requirements: Rust stable, Docker (or PostgreSQL 14+), and a modern browser.

```sh
docker compose up -d postgres
cd backend
DATABASE_URL=postgres://serein:dev-only-change-me@localhost:5432/serein LISTEN_ADDR=0.0.0.0:8080 COOKIE_SECURE=false cargo run
```

Email verification is deliberately disabled by default. To enable registration, configure exactly one provider before starting the API:

- HTTPS mail API: `MAIL_DELIVERY=api`, `MAIL_API_URL=https://api.resend.com/emails` (or a compatible HTTPS endpoint), `MAIL_API_KEY=…`, and `MAIL_FROM='Serein <no-reply@your-domain.example>'`. The API key is sent only as a bearer header to that configured HTTPS origin; redirects, URL user-info/query strings, automatic proxy discovery, response-body logging, and provider error-body logging are disabled.
- SMTP: `MAIL_DELIVERY=smtp`, `SMTP_HOST=…`, `SMTP_TLS_MODE=starttls` with port 587 (default) or `implicit` with port 465, `MAIL_FROM=…`, and optionally both `SMTP_USERNAME` and `SMTP_PASSWORD`. Plaintext SMTP is rejected.

Configure verified sender/domain DNS and provider credentials outside source control. Use a provider key scoped to sending from this domain, place it in the server's secret manager/environment (never the browser/mobile config), and rotate it if it may have appeared in logs or shell history. The server sends it only to the configured provider; it remains in server process memory while running. Only then open `http://localhost:8080`, create an account, retrieve the six-digit code from email, and verify it before sign-in. Codes are hashed, expire after ten minutes, allow five guesses, and have a 60-second resend delay with a per-account daily send cap. These controls are not a substitute for edge/IP rate limiting. The provider setup and email receipt have not been verified here. Registration requires at least eight Unicode characters and no more than 1024 UTF-8 bytes; sign-in does not apply the registration minimum. `/status` shows sanitized API, database, web-interface, and email-provider configuration states; `/healthz` is the machine-readable readiness check. Email status indicates configuration only, so test by registering with an inbox you control and verifying the six-digit code. The account/contact/device flows can be tested with disposable accounts, but messaging is intentionally unavailable: no user-facing chat send path is enabled until a reviewed device-key lifecycle and secure transport are implemented.

For a static frontend hosted separately from the API, set `frontend/web/config.js`'s `apiBase` to the API base URL, configure `ALLOWED_WEB_ORIGINS` on the API to the exact origin(s) of the browser page (scheme, host, and non-default port—not just the API host), use HTTPS/WSS, and keep the frontend/API on the same site (for example, sibling subdomains) so the secure Lax session cookie is sent. The API now rejects disallowed `Origin` headers and emits a CSP plus common security headers on API responses and when it serves the bundled web UI. If the web UI is hosted separately, configure equivalent document security headers there too. This is browser defense-in-depth, not client attestation. Cross-site cookie behavior still needs deployment testing. The web UI uses Rust/WASM username validation when `frontend/web/serein_core.wasm` is built and present; otherwise the local JavaScript fallback is used. CI builds and includes the WASM file in its web artifact.

## First testing phase: local web/API, then mobile

1. Before pushing, keep `.env`, provider credentials, Android keystores, Apple certificates/profiles, and all user data out of Git. Only root `README.md` is tracked Markdown; the complete source ZIP includes ignored documentation. This checkout has no `Cargo.lock`; after installing Rust 1.85+, generate/review one with `cargo generate-lockfile`, then run `cargo check --workspace` and `cargo test --workspace` before committing it.
2. Push `main` to your GitHub repository and wait for **Actions → Checks and mobile builds** to pass. CI uploads the static web app, an Android debug APK plus an unsigned release APK, and an iOS Simulator app zip. Use only `app-debug.apk` for sideload testing. The simulator `.app` zip is not an iPhone IPA.
3. For local web/API testing, use Docker Compose PostgreSQL and the local-only settings in `.env.example`. Copy it to ignored `.env`, then configure a real test-mail provider: `MAIL_DELIVERY=disabled` deliberately prevents registration. From the repo root run `docker compose up -d postgres`; in a second terminal run `cd backend`, `set -a; source ../.env; set +a`, then `cargo run`. Open `http://localhost:8080` and test registration, OTP verification, sign-in, contact requests, settings, and device management with disposable accounts. Use Connection settings to select and check a self-hosted API origin; the web server must allow the exact browser origin. Messaging remains disabled. Detailed checks and the manual smoke-test command are in the ignored `docs/TESTING_GUIDE.md` and in the complete source ZIP.
4. After web/API tests, Android debug installs on API 26+; the CI debug APK is signed with a temporary debug key, not a Play signing key. Android/iOS native messaging is not connected yet. Native apps require a reachable HTTPS API; local `localhost` on a phone refers to the phone itself.
5. For physical iOS device testing, the new manual **iOS Ad Hoc test IPA** workflow requires Apple signing secrets and an unexpired Ad Hoc profile containing the test devices' UDIDs. It creates a test IPA without the stable-release approval gate. The existing `release.yml` remains separately gated and only accepts a stable `X.Y.Z` version/tag; it creates signed Android release outputs and App Store Connect/Ad Hoc iOS IPAs but does not upload to stores.

A green CI run is not a product/security sign-off: the PostgreSQL/mail smoke test is manual, the Rust/mobile builds have not been run in this environment, and native messaging, audited E2EE, attachments, and calls remain incomplete. See `BUILDING.md` (in the complete archive) for artifact and signing details.

## Opaque transfer API (backend only; clients not integrated)

`POST /api/v1/transfers` creates a transfer using an account UUID, chunk count/total ciphertext bytes, and exactly one `{device_id, iv, ciphertext}` encrypted manifest envelope for every active device of both participants. The sender must be authenticated; the recipient must be a verified contact (or the same account). Upload each chunk with `PUT /api/v1/transfers/{id}/chunks/{index}`, `Content-Type: application/octet-stream`, and `X-Chunk-SHA256: <lowercase-or-uppercase hex SHA-256>`. A transfer becomes visible to its devices only after all declared chunks arrive and the aggregate byte count matches. `GET /api/v1/transfers` lists visible transfers; `GET /api/v1/transfers/{id}/chunks/{index}` downloads a chunk; `POST /api/v1/transfers/{id}/ack` acknowledges it; the originating device may `DELETE /api/v1/transfers/{id}` to abort.

Limits are 256 KiB per chunk, 512 chunks / 64 MiB per transfer, 32 active participant devices per transfer, 100 live transfers and 256 MiB of active transfer data per participant, and a seven-day expiry. Upload is resumable and byte-identical repeats are idempotent. SHA-256 is a transport checksum only—not an authenticated E2EE integrity proof. A future client must encrypt the file and manifest locally, include the expected chunk hashes inside the encrypted manifest, verify those hashes and AEAD tags before opening content, and encrypt a manifest/key envelope separately for every device. The API validates envelope shape and device authorization but cannot prove ciphertext is actually encrypted or decrypt it.

## Repository

- `frontend/web/` — static HTML/CSS/JavaScript; no npm runtime packages. Includes first-party `serein-avatar` and `serein-button` Web Components.
- `crates/serein-core/` — first-party zero-dependency Rust domain validators and C/WASM ABI; used by the API and the browser's optional WASM validator. Includes an allocation-free packet framing helper, not a secure transport or integrated network protocol.
- `crates/serein-moq-engine/` — first-party media-track/object router with per-subscriber and aggregate queue bounds; transport-agnostic, not interoperable MOQT on the wire.
- `design/tokens.json` + `scripts/generate-design-tokens.py` — single source for web CSS, Android Java, and iOS Swift design tokens.
- `backend/` — Rust account/session/contact/device APIs, OTP email delivery over HTTPS API or TLS SMTP, authenticated WebSocket/HTTPS message relay, PostgreSQL ciphertext history, and an opaque encrypted attachment-chunk transport. Transfer clients and call media/signaling are not integrated. It uses the shared Rust core. Startup creates/updates schema directly; SQL migrations are not automatically applied.
- `media-transport-spike/` — older isolated WebTransport/QUIC datagram echo experiment; not MoQ and not a calling service.
- `apps/android/` — native Java client with HTTPS auth, contacts, settings, and device-session API wiring; messaging/calls are not connected.
- `apps/ios/` — native SwiftUI client with URLSession auth, contacts, preferences, and device-session API wiring; messaging/calls are not connected.
- `.github/workflows/` — CI and release-artifact workflows; hosted builds/signing have not been verified.

## Development and versioning

`VERSION` is manually maintained and currently `0.4.0-dev.6`, an internal development snapshot—not an Alpha/Beta or release claim. Version bumps are not automatic and a tag does not auto-publish a GitHub Release. A new `version-consistency` CI job runs on every branch/tag push, PR, and manual run; it checks SemVer, all product Cargo package versions, the web version, Android’s `versionName` source, iOS `MARKETING_VERSION` and the What's New version, and platform floors plus exact stable tag matches. On stable version tags it also rejects a version that is not greater than existing stable tags. Signed release jobs require a matching stable `vX.Y.Z` tag and the repository variable `SEREIN_RELEASE_APPROVED=true`; leave it unset until the implementation and release gates are reviewed. Release builds are uploaded as workflow artifacts, not automatically published as a GitHub Release. Dependabot version-update schedules have been removed; dependency bumps are maintainer-driven, while CI resolves/builds dependencies on every push and pull request. GitHub's repository-level security alerts are separate. Markdown notes other than this root README are ignored by Git but remain in the complete source archive.

## Next implementation phases

1. **Opaque transfer transport (implemented in backend source; unbuilt):** upload/download encrypted chunks, per-chunk SHA-256 integrity, resumable idempotent writes, participant/device authorization, quota limits, expiry, and device-specific encrypted manifests. The service sees routing and size/timing metadata but never receives filenames or plaintext. At transfer creation, manifests must cover every currently active device of sender and recipient; devices enrolled later cannot decrypt old transfers yet.
2. **Reviewed key and device lifecycle (not implemented):** choose/integrate a reviewed interoperable E2EE protocol under the dependency policy; bind identity/device keys, verify device additions/revocations, handle key rotation, backup/recovery, replay protection, and multi-device key envelopes. Do not build custom “triple encryption” or a home-grown ratchet.
3. **Client file-transfer integration (not implemented):** encrypt content/manifest on clients using that protocol, persist resumable transfer state locally, stream bounded chunks, verify hashes before decrypting, support pause/retry/ACK, and test cross-platform plus revoked/new-device behavior. Until then, the server transfer API is not exposed as a working attachment feature.
4. **Calls (not implemented):** establish reviewed call signaling and identity-bound session keys, then implement encrypted audio/video over an interoperable QUIC/MoQ stack with congestion control, loss/recovery, device switching, and group limits. The current QUIC echo and object router are not call transports. The current no-new-dependencies-outside-email rule blocks adopting a maintained QUIC/MoQ implementation; do not replace it with custom TLS/QUIC or claim a call works.

## Current limits

- OTP email code paths are implemented but provider credentials, DNS, mail receipt, build, and end-to-end verification are not verified. There is no password reset, account recovery, or IP/edge rate limiting; independent security review is still required.
- The new transfer API is opaque ciphertext storage/routing only. No web/Android/iOS sender or receiver is integrated; it is not a production encrypted-file feature until the reviewed key lifecycle and client work above land. Server metadata (participants, device IDs, byte counts, and timing) is visible.
- Contact discovery by username or verified email now creates a pending request; the recipient must accept. Unknown/ineligible targets get the same response body as eligible targets, and submitters cannot inspect request status before acceptance (to reduce enumeration); requests expire after 30 days and cap at 50 outgoing/100 incoming pending requests; per-account discovery is limited to 10 attempts/hour. Privacy settings control email discovery, request acceptance, and presence; blocks remove the relationship and deny new message/transfer authorization. Timing and distributed abuse resistance are not verified, and there is no trusted edge/IP rate limiter. Mobile-number discovery is not implemented.
- Encrypted messaging is disabled in the current app flow. Legacy shared-passphrase prototype code remains but is not offered to users; there are no verified device keys, audited end-to-end protocol, or key transparency.
- Calls and media are not implemented. The QUIC spike is not a call stack; WebRTC is intentionally excluded.
- Native apps now include account-management API wiring and OTP entry/resend flows, but have no native message encryption/transport or encrypted history store. Android/iOS build outputs and compatibility have not been verified here.
- Existing third-party dependencies remain. Two new crates are permitted only for OTP mail delivery (`lettre` SMTP and `reqwest` HTTPS API); both are exact-pinned and Dependabot is configured to open weekly review PRs. Automated package PRs are not auto-merged. No new crypto, media, QUIC, or MoQ dependencies were added; real interoperable QUIC/MOQT is therefore not implemented.
